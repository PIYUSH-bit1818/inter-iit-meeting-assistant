Scripted — AI Meeting Assistant

Technical report · Inter IIT Tech Meet, ML Bootcamp problem statement
Repository: github.com/PIYUSH-bit1818/inter-iit-meeting-assistant · October 2026

1. Summary

Scripted turns a recorded English meeting into a raw transcript, a refined transcript, meeting minutes, key decisions and action items. A FastAPI backend runs six stages: audio validation and normalization (FFmpeg), speech-to-text (Whisper large-v3 on Groq), transcript refinement (LLM 1, Gemini), meeting documentation (LLM 2, a different Gemini model) and export. A Streamlit interface uploads the recording, shows live progress and presents and downloads every result. Deterministic code checks both language models: a refinement that changes meaning is rejected, and a decision or action item that is not supported by a verbatim transcript quote is withheld instead of shown.

The two language models do different jobs. Refinement is a narrow, high-volume editing task, so it uses a fast Flash model with low thinking. Documentation has to reason across the whole meeting (agreement versus proposal, who owns a task, whether a deadline was stated), so it uses a different model with more thinking. Model IDs were taken from the live Gemini model list for our free-tier key rather than guessed, and every model is configurable in .env (STT_MODEL, REFINE_MODEL, DOCUMENT_MODEL, *_FALLBACK_MODELS). The models that actually served a job are recorded in its output and shown in the UI.

6 · ExportPDF, Word, Markdown, TXT, JSON, CSV21 files
  • Jobs. POST /jobs stores the upload and runs the stages in a background thread. Each stage records its status, start and finish time, message and error code. The UI polls GET /jobs/{id} every second and shows the real stage states, an elapsed clock and a rough time-left estimate.
  • Typed hand-offs. Stages pass strict Pydantic objects (unknown fields rejected): PreparedAudio → RawTranscript → RefinedTranscript → MeetingRecord. The raw transcript is never modified; the refined transcript keeps the same segment ids and timestamps and lists every accepted and rejected change.
  • Traceability. LLM 2 reads the refined text, but its evidence refers to the same segment ids, so every decision and action item can be traced back to the raw speech-to-text output.
  • Exports. All formats are rendered from the same objects (GET /jobs/{id}/exports/{key}), so the human-readable (PDF, Word, Markdown) and machine-readable (JSON, CSV) records always list the same decisions and tasks. The uploaded audio and intermediate files are deleted when the job ends.

4. Preventing hallucination

Refinement guards (per segment)

  • Word-level diff against the raw text. Changes must be small, local replacements (≤ 6 words, ≤ 2 extra words per replacement) that resemble the original (similarity ≥ 0.5; ≥ 0.75 for proper nouns). The whole segment must stay ≥ 0.6 similar.
  • Numbers (including spelled-out forms such as “forty k”), dates, money, negations and modal verbs must be preserved. No new words may be introduced; only filler words (“um”, “uh”) may be dropped.
  • A failing edit is rejected: the segment keeps its raw text and the rejection is reported with its reason.

Documentation grounding checks (per item)

  • The evidence quote must appear in the cited segments, and numbers, dates, money and names in the item must appear in the evidence.
  • A decision needs an explicit, non-negated agreement cue (agreed, decided, approved, confirmed…); otherwise it is a proposal. An action item needs an assignment or commitment.
  • Owner and deadline must be stated in the evidence. Otherwise they are null, shown as “Not specified”, and never guessed.
  • Items that fail are withheld with their reasons (UI “Safety checks” and the complete record), never shown as facts.

6. Verification

  • 348 automated tests (pytest, providers mocked): audio validation and normalization, chunking and segment ownership, refinement guards, grounding checks, schemas, exports (PDF and Word text identical to the JSON record) and API and runner error paths.
  • Browser end-to-end test (Playwright, headless Microsoft Edge): 33/33 checks on a real run. It covers upload, live progress with elapsed time and estimate, the results sections and all 20 downloads, which open and match the UI. It also confirms “Not specified” for missing owners and deadlines, and that no secret or internal path appears in the page or files.
  • Error paths: empty, corrupt, silent, too short, oversized and unsupported files, and provider failures (rate limit, timeout, authentication, invalid output). Each produces a plain-language message with a suggested next step and a stable error code.

7. Engineering notes and limitations

  • Secrets: API keys are read from .env as secret values, never logged or shown in the UI, and .env is excluded from git.
  • Resilience: Gemini calls retry and fall back to the next configured model on 429/503. A long provider outage can still fail a job, with a clear message.
  • No speaker diarization: Whisper does not label speakers, so an owner is assigned only when a name is spoken in the evidence.
  • Scope: English only. Jobs live in memory, so a restart clears them and the app runs as a single process. Uploading compressed audio instead of 16-bit WAV would shorten transcription.
